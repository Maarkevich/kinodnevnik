1. ПРОДУКТ
================================================================================

1.1. Что это

     Личный дневник просмотренного: фильмы, сериалы, мультсериалы, аниме,
     дорамы. Пользователь отмечает «посмотрел», ставит оценку от 0,5 до 5,0
     шагом 0,5, пишет заметку, добавляет в отложенные, ведёт свои списки.
     Приложение показывает статистику его вкуса. Метаданные — из TMDb.

1.2. Принципы, важнее функциональности

     П1. Приватность по умолчанию. Аккаунта нет. Сервера нет. Данные живут
         только на устройстве. Любая синхронизация — только между устройствами
         самого пользователя и только по его явной команде.
     П2. Офлайн — основное состояние, а не fallback. Приложение обязано быть
         полностью полезным без сети: дневник, списки, оценки, аналитика,
         постеры из кэша. Сеть нужна только для поиска и новых тайтлов.
     П3. Русский язык — родной, а не переведённый. Никакого английского UI не
         существует даже как запасной вариант (см. раздел 4).
     П4. Честность цифр. Лучше «нет данных», чем красивая выдуманная цифра.
     П5. Одна рука. Главное действие (записать просмотр) доступно с нижнего
         края экрана большим пальцем.

1.3. Целевые платформы (все три — обязательны)

     - Android: Chrome / Android WebView, установленное PWA.
     - iOS: Safari, установленное на домашний экран (add to home screen).
       Это самая требовательная платформа, см. раздел 12.
     - Desktop: Chrome / Edge / Firefox, ширина до 1440 px.

1.4. Чего в продукте НЕТ (осознанно, не «пока не реализовано»)

     - Учётного записей, профилей, соцсетей, лент других людей.
     - Бэкенда, собственной СУБД, облачного хранилища.
     - Импорта/экспорта Letterboxd (у пользователя нет аккаунта — см. 2.2).
     - Подсчёта суммарного времени просмотра (пользователю не важно — см. 2.3).
     - Платформ, подписок, рекламы, аналитики поведения, телеметрии.
     - Светлой темы как равноправной (см. 5.2).
     - Многоязычности как фичи (см. 4.1).

4. ЯЗЫК: РУССКИЙ КАК ИСХОДНОЙ
================================================================================

4.1. Решение

     Русский — единственный язык продукта. Строки пишутся в шаблонах и коде
     СРАЗУ по-русски. Никакого переводческого слоя.

4.2. Почему не @angular/localize и не ngx-translate

     i18n-слой нужен, когда языков больше одного или когда надо пуллить апстрим
     и переводить независимо. Здесь обоих условий нет (язык один, апстрим
     берётся один раз как донор). Слой обошёлся бы: 405 автоматически
     расставленных маркеров, 333 единицы перевода, отдельный XLIFF-пайплайн,
     сборка с --localize, перестройка CI, — и не дал бы ничего.
     Это решение зафиксировано; если оно понадобится позже, путь назад описан
     в 4.6.

4.3. Что при этом обязательно

     - В index.html: <html lang="ru">.
     - LOCALE_ID = 'ru' (providers в app.module.ts: { provide: LOCALE_ID,
       useValue: 'ru' }) + registerLocaleData(ru) из @angular/common/locales/ru.
       Это нужно ДАЖЕ без i18n-слоя: от LOCALE_ID зависят DatePipe,
       DecimalPipe и плюралы в Intl.
     - Все форматтеры чисел/дат — через Intl/Angular pipes без жёсткой локали.
       В доноре 6 мест с захардкоженным 'en-US' (analytics-format.ts:12,19,20,
       122; log-sheet.component.ts:145; world-map.component.ts:44) — все убрать.

4.4. Правила русской типографики в UI (обязательны)

     - Регистр: sentence case. «Дата просмотра», а не «Дата Просмотра». В
       доноре заголовки в Title Case — при переносе переводить в sentence case.
     - Кавычки: «ёлочки».
     - Тире: – или —, дефис только в составе слов («кино- и телеиндустрия»).
     - Пробел перед %: «12,5 %». Разделитель тысяч — неразрывный пробел:
       «4 567». Десятичный разделитель — запятая: «4,3».
     - Сокращения единиц времени: ч, мин, сут. (без точки у ч и мин).
     - Обращения: на «вы» со строчной буквы.
     - Никаких эмодзи в интерфейсе (в доноре их нет — сохранить).
     - Названия языков и стран — через Intl.DisplayNames(['ru'], ...), не
       руками (см. 6.4: это удаляет 132 строки из донора).

4.5. Что НЕ переводить

     Названия брендов и сервисов: TMDb, Netflix, Okko, Кинопоиск (уже русское),
     Apple TV, More TV, Premier, Amediateka, Crunchyroll, MUBI, YouTube.
     Имена собственные людей — транслитерировать из TMDb (он отдаёт русские),
     при отсутствии русской версии показывать оригинал.

4.6. Путь назад (если многоязычность всё же понадобится)

     Маркеры i18n расставляются автоматически скриптом (405 маркеров за один
     прогон, доказано: после снятия маркеров html.parser даёт идентичный
     токен-стрим для 45/45 шаблонов, т.е. разметка недеструктивна). Ключи —
     хэш от текста, поэтому одинаковые фразы сливаются в одну единицу
     (405 сайтов → 333 уникальные, 0 коллизий). Но в v1 это не делать.

5.2. Светлая тема — решение

     Полноценной светлой темы в v1 НЕТ. Причина измерена: акцент #49effb на
     светлом фоне даёт 1.28:1 (провал), затемнённый #0b7d8c — только 4.45:1
     (AA для крупного), #076d7a — 5.54:1, но тогда это уже другой бренд.
     Реализовать:
       - системная тема игнорируется, приложение всегда тёмное;
       - в index.html и manifest theme_color = #16191c;
       - в CSS не оставлять @media (prefers-color-scheme: light) веток —
         удалить из донора всё, что они касаются (html.light, --ion-...
         overrides для light);
       - в настройках переключатель темы УБРАТЬ (в доноре theme: system|light|
         dark) — оставить одну тему. Это убирает ~15 строк настроек и все
         связанные тесты.

5.3. Типографика

     Семейство: Nunito (переменный, wght 200–1000), self-hosted.
     Подмножества: latin, latin-ext, cyrillic, cyrillic-ext — все есть
     (проверено по unicode-range Google Fonts: U+0400, U+0460, U+0490).
     DONOR FONTS НЕ ПЕРЕНОСИТЬ: Fraunces, Sora, Space Grotesk, Outfit —
     у всех четырёх кириллицы нет ни в одном подмножестве (проверено),
     русский текст молча откатится на системный шрифт и в одной строке
     будут две гарнитуры.

     Раздача: woff2, локально в assets/fonts/, НЕ с fonts.googleapis.com —
     приложение офлайн, первый запуск без сети обязан выглядеть правильно.
     @font-face с font-weight: 200 1000 (variable), font-display: swap.
     Файл: Nunito[wght].subset-cyrillic.woff2 + subset-latin.woff2,
     unicode-range обязаны быть указаны, иначе браузер тянет всё.

     Шкала (фиксирована; в доноре шкалы нет — размеры расставлены по месту
     вроде text-[1.05rem], это ликвидировать):

       --kd-fs-card    17px / 700 / 1.25   название тайтла в карточке
       --kd-fs-body    15px / 400 / 1.45   основной текст
       --kd-fs-small   13px / 600 / 1.35   подписи, мета
       --kd-fs-micro   11px / 700 / 1.2    eyebrow-подписи, UPPERCASE
       --kd-fs-num     20px / 800 / 1.0    цифры статистики, tabular-nums
     Обязательное: font-variant-numeric: tabular-nums для всех числовых
     ячеек статистики, иначе колонки «плывут».

     Цветовые акценты в заголовках (требование пользователя):
       - В H1/H2 акцентным цветом выделяется ОДНО смысловое слово или цифра,
         не более. Реализация — спан с классом .accent, переводимый текст
         обязан оставаться целиком внутри <ng-container>, чтобы не рвать
         связность (см. 4.6 при переносе).
       - Числа в статистике — всегда --kd-accent, подписи к ним —
         --kd-text-muted. Это даёт «акцент в названиях и заголовках», о котором
         просил пользователь, не превращая экран в салют.
       - Запрещено: градиентный текст, -webkit-text-fill-color, обводка.

5.4. Радиусы (требование: «везде скруглённые края»)

       --kd-r-sm     8px    input, чипы, бейджи, mini-карточки
       --kd-r-md    14px    кнопки, карточка постера, поля форм
       --kd-r-lg    20px    карточка-секция, модалка снизу, popover
       --kd-r-xl    28px    sheet, крупный оверлей, hero-обложка снизу
       --kd-r-full  999px   переключатели, pill-табы, аватар
     Постеры: 14px. Обложки 2.35:1: 20px только у нижних двух углов.
     Прогрессивное улучшение (не обязательно, не ломать сборку):
       corner-shape: superellipse(1.6);   /* там, где поддерживается */

5.5. «Жидкое стекло» — как делать и где НЕ делать

     Донор уже использует backdrop-filter: saturate(125%) blur(12px) в 13
     файлах — не изобретать, а формализовать в один слой.

     Миксин (единственный источник правды, scss-миксин, а не копипаста):
       @mixin kd-glass($blur: 20px, $alpha: .72) {
         background: rgba(33,37,41, $alpha);
         -webkit-backdrop-filter: blur($blur) saturate(160%);
         backdrop-filter: blur($blur) saturate(160%);
         border: 1px solid rgba(255,255,255,.10);
         box-shadow: inset 0 1px 0 rgba(255,255,255,.14),
                     0 12px 32px -12px rgba(0,0,0,.6);
       }

     ОБЯЗАТЕЛЬНЫЕ ограничения (это не косметика, а корректность и скорость):
       1. Минимальная альфа 0.72. Расчёт: при альфе 0.55 эффективный фон
          #2a2e33, текст #ced4da = 9.14:1 — ок; но стекло поверх СВЕТЛОГО
          постера даёт эффективный #6b7280 → текст 3.24:1, акцент 3.46:1 —
          ПРОВАЛ. Поэтому под любым стеклянным слоем, за которым может быть
          изображение, обязателен затемняющий скрим:
            linear-gradient(rgba(0,0,0,.55), rgba(0,0,0,.65))
          и мелкий текст (<=13px) на стекле поверх изображения не размещается
          вообще.
       2. @supports not (backdrop-filter: blur(1px)) → сплошной фон
          var(--kd-bg-elevated), без border-подсветки.
       3. @media (prefers-reduced-transparency: reduce) → то же самое.
          Это не fallback для старых движков, а уважение настройки пользователя.
       4. Не более 2 одновременно видимых слоёв со backdrop-filter.
          Следствие: стекло — для overlay (sheet, modal, popover, dropdown,
          тулбар, таббар) и НЕ для каждого постера в сетке. Карточки в
          контенте — обычная подложка --kd-bg-elevated + радиус + тень.
          Сетка 3×6 постеров со blur = 18 слоёв = гарантированные джарки на
          Android среднего класса и iPhone.
       5. Ionic-оверлеи настраиваются через их собственные переменные, а не
          только CSS: --backdrop-filter у ion-modal/ion-popover недоступен,
          поэтому стиль задавать через ::part(content) / .popover-content и
          customProps при create().

     Где стекло обязательно (по требованию пользователя — «окна, карточки,
     выпадающие списки»):
       - log-sheet (лист быстрой записи) — полностью;
       - все ion-modal (быстрая запись, выбор обложки, импорт);
       - все ion-popover и ion-select dropdown (в т.ч. выпадающий список
         языков/жанров);
       - ионические alert (подтверждения удаления) — через cssClass
         kd-alert-glass;
       - тулбар и таббар — стекло поверх контента при скролле (как в доноре);
       - плашка «офлайн» — стекло.
     Где НЕ делать: сетки постеров, карточки списка, страницы-экраны целиком,
     графики (blur под SVG убивает читаемость).

5.6. Компонентные правила, унаследованные от донора (сохранить)

     - Обложка профиля: aspect-ratio 2.35/1, w780 на телефоне, w1280 на
       ≥768px, градиентный фолбэк если картинки нет.
     - Единый <kd-list-card> (коллаж из 4 постеров, scale(.97) при нажатии)
       для всех входов в коллекции — в доноре это уже сделано, не дублировать.
     - Таббар и тулбар: 56px + safe-area, не менять.
     - Графики: инлайновый SVG, без библиотек.
     - touch-action: manipulation + :active transform для отклика 0 мс.

6.1. Структура (изменена относительно донора по решению пользователя)

     Нижняя панель, 5 мест:
       [ Дневник ] [ Подборки ] [ ⊕ ] [ Поиск ] [ Профиль ]
     Ключевое изменение: первая вкладка — Личный дневник, а не TMDb-тренды.
     Обоснование: продукт про данные пользователя; побочный эффект — главная
     перестаёт зависеть от сети и перестаёт существовать баг донора
     «пустой экран при 500/офлайне» (подтверждён в их аудите как незакрытый).

     Роуты:
       /diary        Дневник (вкладка 1, дефолт)
       /collections  Подборки (вкладка 2) — сюда переезжает весь Explore
       /search       Поиск (вкладка 4)
       /profile      Профиль + аналитика (вкладка 5)
       ⊕             модалка быстрой записи (не роут)
       /movie/:id, /tv/:id, /person/:id, /movie/:id/reviews,
       /tv/:id/season/:n, /list/:id, /settings, /edit-profile — как в доноре.

6.2. Экран «Дневник» (главный)

     Сверху вниз:
       1. Заголовок «Дневник» + счётчик записей (число акцентным цветом).
       2. Блок «Сегодня / Эта неделя» — компактная строка: N за сегодня,
          M за неделю, streak (подряд дней с записью). Если 0 — блок не
          показывается, экран начинается с ленты.
       3. «Смотрю сейчас» — горизонтальная лента сериалов/франшиз с
          незавернённым прогрессом (см. 6.6 про статусы).
       4. Лента записей, сгруппированная по месяцам («Ноябрь 2026»), внутри
          месяца — по дням. Строка: постер 48px, название (1 строка,
          truncate), оригинальное название серым мелким, если не совпадает,
          звёзды, дата «5 нояб.», чип «пересмотр», чип «сериал · S02E05».
       5. Фильтры: чипы «Все / Фильмы / Сериалы / Мультфильмы / Аниме /
          Дорамы», сортировка (новые/старые/рейтинг/алфавит).
     Пустое состояние: не «No diary entries yet», а «Здесь появятся твои
     записи. Нажми ⊕ и отметь первый фильм.» с крупной кнопкой.
     Обязательные состояния: загрузка (скелетон), ошибка сети (не пустой
     экран!), пусто, отфильтровано-в-ничего.

6.3. Экран «Подборки»

     Сюда переносится Explore из донора: тренды, популярное, top rated,
     скоро, «похожие на просмотренное», случайное из отложенных.
     Категории — не захардкоженные вкладки, а конфиг (раздел 7).
     Сегменты Movies/TV в доноре заменяются на единый поток с чипом типа,
     потому что у пользователя смешанное потребление (сериалы + мультсериалы +
     дорамы), и переключать контекст ради поиска аниме — лишнее действие.

6.4. Экран «Поиск»

     Как в доноре, плюс:
       - поиск по меткам и по собственному тексту рецензий (в доноре — только
         по названию);
       - нормализация ввода: ё→е регистронезависимо;
       - ТРАНСЛИТ с русской раскладки: fkmrf → «фильм», cnfе → «сериал».
         Реализовать таблицей соответствия, это лечит жалобу «поиск не
         работает» при полностью правильном переводе.
       - recent searches, как в доноре.

6.5. Экран «Профиль»

     Шапка с обложкой (2.35:1), аватар, имя, «о себе», счётчики.
     Ниже — вход в коллекции одним компонентом (избранное, отложенные,
     понравившееся, свои списки, рецензии, дневник).
     Аналитика — 5 вкладок, как в доноре (имена на русском):
       Обзор | Оценки | Активность | Люди | Жанры и страны
     ВНИМАНИЕ: в коде донора карта стран УЖЕ ЕСТЬ (app-world-map подключён в
     profile.page.html:598, работает по SVG с двухбуквенными ID), хотя в их
     же аудите написано «never built». Доки донора устарели — спецификацию
     строить по коду.

6.6. Статусы (НОВОЕ, в доноре отсутствует)

     Пользователь просил. Модель: у записи просмотра есть необязательный
     статус из { ', watching', 'rewatching', 'dropped' } — на русском
     «Смотрю», «Пересматриваю», «Брошено». Хранится в WatchedEntry.status.
     - «Смотрю/Пересматриваю» = запись активна, но просмотр не завершён:
       не участвует в «просмотрено», участвует в «Смотрю сейчас» (6.2.3).
     - Завершение (тап по активной записи → «Завершить») превращает её в
       обычную запись дневника с датой окончания.
     - Сериалы: статус attaches к сериалу, прогресс = количество отмеченных
       серий (уже есть в доноре: settings.episodeWatched, ключ
       `${tvId}-${season}-${episode}`).
     - Дropped обязателен: без него «недомотренное» неотличимо от «смотрю»,
       и очередь отложенного не имеет смысла.

     Оставить: имя, био, аватар, обложка, «Без 18+», «Затенять просмотренное»,

7. ИСТОЧНИКИ ДАННЫХ И КАТЕГОРИИ

7.1. Единственный источник метаданных — TMDb

     Обоснование проверено на живом API (ключ из донора, v3):
       - русские названия отдаются: фильмы 90%+ (топ-20 по популярности),
         сериалы en/ru/es 90–100%, мультсериалы 90%, аниме 85%;
       - альтернативные названия и переводы доступны отдельными ручками
         (/alternative_titles, /translations);
       - «где смотреть» для региона RU работает: /watch/providers/movie?
         watch_region=RU отдаёт 36 провайдеров, среди них Okko(115),
         Amediateka(116), Кинопоиск(117), More TV(557), Premier(570),
         Crunchyroll(283), MUBI(11), Apple TV(350); по конкретным фильмам
         данные есть (Avengers: Endgame → More TV + Кинопоиск;
         «Унесённые призраками» → Okko).
       - конфигурация /configuration НЕ содержит список стран, и у
         Fight Club (id 550) региона RU в providers нет вообще — покрытие
         рваное, это норма, UI обязан это переживать (см. 7.6).

     НЕ использовать как источники (проверено, отказ обоснован):
       - Кинопоиск: публичного API нет (www.kinopoisk.ru/api/1.x → 404,
         api.kp.org не резолвится).
       - AniList GraphQL: работает (HTTP 200), но формата DRAMA в enum
         MediaFormat НЕТ (только TV, TV_SHORT, MOVIE, SPECIAL, OVA, ONA,
         MUSIC, MANGA, NOVEL, ONE_SHOT), а countryOfOrigin=KOREA ничего не
         отдаёт → дорамы не покрывает совсем.
       - MyDramaList / Viki / Kocowa: публичного API нет.

7.2. Shikimori — вспомогательный источник, только для аниме

     API живой (https://shikimori.one/api/animes), требует User-Agent,
     отвечает после 301 (нужен follow redirects). Покрытие русскими
     названиями: 30/30 в топ-30 по популярности — лучше TMDb (85%).
     Поиск по-русски работает («Наруто» → id 20).

     ЖЁСТКОЕ ОГРАНИЧЕНИЕ (проверено и это причина, почему нельзя «просто
     подтягивать откуда попало»): для не-аниме Shikimori даёт ЛОЖНЫЕ
     СРАБАТЫВАНИЯ. Корейские шоу без русского названия, посланные в поиск по
     оригинальному имени, вернули: «무한도전» → «Мы — детективы»,
     «쇼! 음악중심» → «Цирковое шоу Грами», «TV 동물농장» → «Физиология
     извращенцев». 4 из 8 «совпадений» — мусор.
     Поэтому: Shikimori опрашивается ТОЛЬКО когда тайтл одновременно
       media_type === 'tv' И original_language === 'ja' И жанры содержат 16,
     и результат принимается только при совпадении года релиза ±1 И
     совпадении хотя бы одного альтернативного названия. Иначе — молчать.

7.3. Категории — это конфиг, а не код

     Ключевой факт: жанра «дорама» в TMDb НЕТ. Поиск keyword по «дорама»,
     «kdrama», «k-drama» не даёт ничего (по «k-drama» возвращаются чужие
     keyword'ы cdrama/jdrama/drama). Фильтр сетами тоже бесполезен:
     with_networks=1156 (tvN) → total=0, 246 → 0, 391 (Fuji TV) → 457.
     Значит «Дорамы» — наша сохранённая подборка = комбинация фильтров.

     Файл src/app/data/collections.config.ts — массив объектов:
       { id, title, kind: 'movie'|'tv', filters, sort, manualInclude?: TMDbId[] }

     Стартовый набор (значения фильтров измерены, % — доля русских названий
     в топ-60 по популярности):

       id            название        filters                                     total   RU
       --------------------------------------------------------------------------- ----- ----
       animation-tv  Мультсериалы    tv, with_genres=16                          15716   90%
       animation     Мультфильмы     movie, with_genres=16                       20001+  90%
       anime         Аниме           tv, ja, with_genres=16                       5500   85%
       kdrama        Корейские       tv, ko, with_genres=18|10749                —       75%
       cdrama        Китайские       tv, zh, with_genres=18                       —      53%
       tdrama        Тайские         tv, th, with_genres=18                       —      51%
       jdrama        Японские дорамы tv, ja, without genre 16, with_genres=18     —       ~80%
       turkish       Турецкие        tv, tr                                       2532   80%
       spanish       Испанские       tv, es                                       7933   90%
       russian       Русские         tv, ru                                       4648  100%
       reality       Реалити/ток-шоу tv, with_genres=10764|10767                  —      21%
       ---------------------------------------------------------------------------
       (20001 = потолок выдачи TMDb, реальное число больше)

     ВАЖНО про дорамы: без жанрового фильтра «ko» даёт 50% русских названий,
     с фильтром по драме — 75%; реалити и ток-шоу — 21% и 6% (это корейские
     «라디오스타», «무한도전» и т.п., у них русских названий нет в природе).
     Отсюда правило: категорию «Дорамы» строить СТРОГО с with_genres=18|10749,
     иначе в неё свалится корейское ТВ-шоу без перевода.

     Категории — данные, не разметка: добавление новой категории не должно
     требовать правки компонентов.

7.4. Отображение названия (главный UX-риск проекта)

     25–50% азиатского каталога TMDb не имеет русского названия, и
     дозагрузить его некуда (7.2). Правило отображения, обязательное:
       - если русское название есть → показываем его, а оригинал — второй
         серой строкой 11–13px (или по настройке «Показывать оригинальные
         названия»: всегда / только при несовпадении / никогда);
       - если русского нет → показываем оригинал ПЕРВЫМ, и он не считается
         «непереведённым» — это корректное состояние;
       - поиск обязан находить тайтл и по оригинальному названию тоже
         (в снапшоте храним оба поля — см. 8.3).
     Никаких транслитераций «на лету» и автоматических переводов.

7.5. Русификация кодов стран и языков

     В доноре это подтверждённый баг: ISO-коды рисуются сырьём (EN, cn, xx).
     Реализация: Intl.DisplayNames(['ru'], {type:'language'|'region'}) +
     нормализация «особых» кодов TMDb: cn→zh, xx→«без страны», «»→пропуск.
     Фолбэк при отсутствии DisplayNames (старый WebView): code.toUpperCase().
     В доноре фолбэк есть не везде (world-map.component.ts:44 — Intl создаётся
     с ['en'] и без try/catch) — переносить с правкой.

     Удалить из настроек массив LANGUAGE_OPTIONS (132 захардкоженных названия
     языка + сортировка по английскому) — генерировать из Intl и сортировать
     localeCompare(..., 'ru').

7.6. «Где смотреть»

     Блок на экране тайтла, из /{movie|tv}/{id}/watch/providers.
     Регион по умолчанию RU (наследуется из настройки region).
     Обязательное поведение: если в ответе нет ключа 'RU' — блок НЕ
     показывается целиком (не «нет данных» посреди экрана). Данные рваные по
     природе (Fight Club: RU отсутствует, Avengers: RU есть) — это не ошибка.
     Группировки: «Подписка», «Покупка», «Аренда» (+ ссылка TMDb).
     Провайдерские логотипы — с image.tmdb.org, кэшируются как постеры (11.3).

================================================================================
8. МОДЕЛЬ ДАННЫХ И ХРАНИЛИЩЕ
================================================================================

8.1. Почему IndexedDB, а не localStorage донора

     Донор хранит всё в localStorage и считает квоту 10 МБ
     (user-data.service.ts:2108 `const standardQuota = 10 * 1024 * 1024`),
     с обработчиком переполнения, который сносит кэш TMDb и показывает
     «Storage quota exceeded». Реальная квота localStorage в браузерах —
     5 МБ, и это на грани уже при нескольких тысячах записей с снапшотами.
     В PWA добавляется риск потери данных (12.1). Поэтому: IndexedDB.

8.2. Схема базы

     Имя: kinodnevnik, версия 1.
     Stores:
       entries      keyPath entryId        idx: byMedia(media_type+id),
                                              byWatchedAt, byStatus, byUpdated
       watchlist    keyPath key            (media_type:id)       idx: byAdded, byUpdated
       favorites    keyPath key            (media_type:id)       idx: byOrder
       lists        keyPath id                                   idx: byUpdated
       listItems    composite key [listId, mediaKey]             idx: byList
       profiles     keyPath id            (1 запись — сам профиль)
       settings     keyPath k
       titles       keyPath mediaKey      (локальные снапшоты метаданных)
       overrides    keyPath mediaKey      (ручные правки названия — 8.5)
       tombstones   keyPath key           (удаления — 9.3)
       tmdbCache    keyPath cacheKey      (ответы API; volatile)
       imageQueue   keyPath url           (очередь скачивания постеров)

     Все значения — объекты без циклов. Даты: ISO-строки (YYYY-MM-DD для
     календарных дат, полный ISO для временных меток).

8.3. WatchedEntry (совместимо с донором + новое)

     Поля донора сохраняются как есть: entryId, id, media_type, title,
     poster_path, watchedAt, dateUnknown, approximateDate, importerCreated,
     userEdited, rewatch, rating (0.5–5.0 шаг 0.5), review, tags, liked,
     sourceKey, release_date, first_air_date, snapshot.

     НОВОЕ (обязательно, без этого невозможен раздел 9):
       titleOriginal: string        оригинальное название (7.4)
       titleRu: string | null       русское, если известно
       status: 'watching'|'rewatching'|'dropped'|null   (6.6)
       progress: { season, episode, total } | null      для «Смотрю»
       createdAt: ISO
       updatedAt: ISO               ОБЯЗАТЕЛЬНО — часы конфликта (9.4)
       schema: 2

     snapshot (снимок метаданных на момент записи) — то, что делает возможным
     офлайн и спасение при 404: id, title, poster, backdrop, release_date,
     runtime_minutes (сохраняем, но не суммируем — 2.3), genres, directors,
     tmdbVoteAverage, tmdbVoteCount, original_language, production_countries.

8.4. Ключи и дедупликация (решает главную проблему синхронизации)

     entryId — UUID, генерируется на устройстве. Следствие из кода донора
     (importBackup, строки 1757–1763: currentWatched[entryId] = {...}):
     один и тот же фильм, записанный независимо на телефоне и ноутбуке, —
     это ДВА разных entryId, то есть после слияния ДУБЛЬ, и аналитика
     посчитает его дважды.

     Поэтому вводится семантический ключ:
       dedupKey = `${media_type}:${id}:${watchedAt || 'na'}:${rewatchSeq}`
     где rewatchSeq — номер пересмотра в рамках одного (media, date).
     Слияние (9.2) схлопывает записи по dedupKey, а не по entryId,
     и НИКОГДА не схлопывает по dedupKey, если у обеих записей
     dateUnknown === true (иначе потеряем легитимные пересмотры без даты).

8.5. Ручные переопределения

     overrides: { mediaKey, titleRu, note, updatedAt } — то, что пользователь
     вписал сам, если источник не дал русское название. Имеет наивысший
     приоритет при отображении. Не отправляется никуда, кроме его собственного
     бэкапа.

8.6. Миграция

     При старте: если в localStorage есть ключи донора (mva_*, tmdb_cache_v2)
     — выполнить однократную миграцию в IndexedDB, после чего оставить
     localStorage-ключи нетронутыми на 30 дней под именем
     mva_migrated_backup_* (страховка от кривой миграции), и показать один
     тост «Данные перенесены». Миграция идемпотентна.
     Поля, которые донор писал, а мы больше не пишем (runtimeMinutes в
     snapshot, primaryColor, theme) — при миграции молча игнорируются,
     НЕ удаляются из типа (старые бэкапы должны читаться вечно).

9. ИМПОРТ/ЭКСПОРТ = СИНХРОНИЗАЦИЯ (требование пользователя)

9.1. Формулировка требования

     «Импорт/экспорт должно работать как синхронизация: при импорте бэкапа
     добавляется только то, чего нет, без повторов.»
     Это значит: импорт идемпотентен, повторный импорт того же файла не
     создаёт дублей, и импорт с другого устройства не возвращает удалённое.

9.2. Алгоритм слияния (обязателен именно в этом порядке)

     Для каждой коллекции:
       1. Индексировать локальные записи по dedupKey (8.4), а не по entryId.
       2. Для каждой входящей записи:
          a) dedupKey нет локально → вставить как есть (сохранить entryId
             источника — это важно для идемпотентности).
          b) dedupKey есть → слить поля по правилам 9.4, обновить updatedAt.
          c) ни одного «добавить вторую копию» — никогда.
       3. Отдельный проход по tombstones (9.3): если удалённая запись есть
          среди входящих и не редактировалась позже удаления → НЕ восстанавливать.
       4. Всё в одной транзакции IndexedDB. Провал любой части = откат всего.
       5. Перед записью — обязательный snapshot текущего состояния (в доноре
          это saveBackupSnapshot в sessionStorage, строки 1903–1912 — заменить
          на store 'snapshots', sessionStorage для этого не годится, см. 12.4).

     Идемпотентность проверить тестом: import(X) → import(X) → import(X)
     даёт то же состояние, что один импорт. Это автотест, не рассуждение.

9.3. Tombstones (без них «синхронизация» врёт)

     Удаление НЕ физическое: в tombstones пишется
       { key: dedupKey, deletedAt: ISO, lastKnownUpdatedAt: ISO }.
     Удалённая запись перестаёт отображаться, но остаётся в базе 90 дней.
     При слиянии: входящая запись с dedupKey, помеченным как удалённый позже,
     чем её updatedAt, отбрасывается.
     Записи старше 90 дней из tombstones вычищаются.
     Причина обязательности: в модели донора нет ни updatedAt, ни deletedAt
     (проверено грепом: только addedAt), поэтому сегодня импорт с другого
     устройства ВОССТАНОВИТ удалённое. Это не «недочёт», это отсутствие
     синхронизации; чинится до переезда на IndexedDB, а не после.

9.4. Разрешение конфликтов (одно и то же поле изменено на двух устройствах)

     Иерархия правил, применить по порядку:
       1. userEdited === true у одной из версий → она выигрывает целиком
          (намеренная ручная правка важнее импорта).
       2. иначе — побеждает версия с бо́льшим updatedAt (LWW).
       3. поля, которые можно объединять без спора, мержим множеством:
          tags (объединение), список принадлежностей к коллекциям,
          episodeWatched (объединение по ключу серии).
       4. поля-скаляры (rating, watchedAt, review, liked, status) — не
          мержатся, а берутся из победившей версии.
       5. при равных updatedAt — локальная версия, и это логируется в
          отчёт импорта (не молча).
     Правило 1 существует потому, что в доноре userEdited уже есть в модели;
     использовать его дешевле, чем изобретать часы.

9.5. Слияние при несовпадении названий одного и того же тайтла

     Если у двух записей совпадают media_type+id, но разные watchedAt —
     это НЕ конфликт, это два просмотра (пересмотр). Если совпадают и даты,
     но разные названия (например, переименование в TMDb) — сравнивать по
     normalized title (утилиты из удалённого tmdb-matcher.ts, 2.2), и при
     похожести >0.9 считать одной записью.

9.6. Экспорт

     Формат: JSON, version 2, gzip через fflate → .json.gz, с явным
     подтипом. Содержит ВСЕ stores кроме tmdbCache и imageQueue (кэш — не
     данные пользователя), включая tombstones и overrides.
     Имя файла: kino-dnevnik-YYYY-MM-DD-HHmm.json.gz
     В файле — НИКАКИХ токенов и API-ключей (15.3).

9.7. UI синхронизации

     В настройках один раздел «Синхронизация»:
       - «Выгрузить файл» / «Загрузить файл»;
       - последняя выгрузка: дата;
       - после импорта — отчёт: добавлено N, обновлено M, пропущено дублей K,
         восстановлено после удаления 0, конфликтов P (и список P по тапу);
       - отмена импорта (undo) — через snapshot из 9.2.5.
     Никаких слов «слияние», «replace», «merge with existing» как выбор
     пользователя: слияние — единственное поведение, «заменить всё» остаётся
     только в опасной зоне («Удалить все данные»).

     Числа: 4 567 (неразрывный пробел), 4,3★, 12,5 % (пробел перед %).

     Календарь: неделя от понедельника — в доноре уже так (activity-calendar:
     Mon/Wed/Fri; CalendarDate: 0 = Monday), сохранить.

11.2. Service worker — писать руками, НЕ @angular/pwa

     Причина: ngsw не умеет (а) фоновое докачивание постеров в IndexedDB,
     (б) корректная деградация при переполнении квоты, (в) двойной cache
     (данные пользователя ≠ кэш API). Пишется свой sw.ts (~200 строк),
     компилируется отдельным entry в angular.json.

     Стратегии:
       - App shell (index.html, *.js, *.css, шрифты, иконки): cache-first,
         прекеш списком, который ГЕНЕРИРУЕТСЯ из сборки. Кэшировать только
         реально существующие файлы — добавление несуществующего пути в
         cache.addAll валит активацию SW целиком (это уже случалось в другом
         проекте этого пользователя, avtoklavi: 146 картинок уронили SW).
       - Ответы TMDb: network-first с таймаутом 4с, фолбэк в кэш, и
         ОДНА запись на ключ запроса (ключ = path + все query, включая
         language — в доноре cacheKey это уже делает правильно,
         tmdb.service.ts:85–92, перенести).
       - Постеры/бэкдропы: stale-while-revalidate, лимит 600 записей, LRU.
         Бэкдропы — только w780 на телефоне, w1280 на ≥768px (как в доноре).
       - Файлы пользователя: не кэшируются.

     Обязательное:
       - skipWaiting НЕ включать. Обновление — по явной кнопке.
       - при activate — чистка старых версий кэша.
       - quota: перед кэшированием картинки проверять navigator.storage
         .estimate(); при usage > 60% от quota — вытеснять LRU, при
         невозможности — молча пропускать кэш (не валить запрос).
       - обработка errors в fetch-обработчике: network failure → cache,
         cache miss → offline-заглушка для навигации (./offline).

11.3. Картинки

     Все изображения TMDb идут через один сервис PosterService, который:
       1) отдаёт blob из IndexedDB, если есть;
       2) иначе сетевой URL, и параллельно кладёт в кэш (через imageQueue,
          батчами по 20, в idle, НЕ в момент скролла — иначе джарки);
       3) при отсутствии сети и кэша — градиентная заглушка с первой буквой
          названия (в доноре градиентный фолбэк обложки уже есть).
     Это нужно потому, что image.tmdb.org в офлайне недоступен, а дневник без
     постеров выглядит сломанным.

11.4. Обновление приложения и метка версии

     - SW находит новую версию → вверху ненавязчивый баннер
       «Доступно обновление» + кнопка «Обновить» (postMessage SKIP_WAITING →
       location.reload()). Не авто-перезагружать посреди ввода данных.
     - Если обновление найдено при старте и пользователь ничего не трогает —
       применить на следующем закрытии вкладки (notificationclick/reload).
     - Метка версии: в настройках «Версия 0.1.0 (сборка <sha7>)», значение из
       environment, генерируется prebuild-скриптом. Это требование
      пользователя из его прошлого PWA-опыта (автоклав): автообновление SW +
       видимая метка версии.

11.5. ВЕРСИОННОСТЬ ФАЙЛОВ И ОБНОВЛЕНИЕ (требование пользователя: «изменили
      файл на GitHub — PWA подтянул его сразу»)

11.5.1. Жёсткое ограничение платформы (проверено эмпирически)

     GitHub Pages отдаёт ВСЕ ответы с фиксированным
       Cache-Control: max-age=600
     (замерен на HTML, на .js и на sw.js; переопределить нельзя — механизма
     custom headers у Pages нет, файл _headers не поддерживается).
     Следствие: полагаться на HTTP-кэш для свежести БЕСПОЛЕЗНО. Максимум, что
     даёт сам Pages, — задержка до 10 минут для первого визита без SW.
     Поэтому свежесть обеспечивает service worker, а не сервер.

11.5.2. Обязательная схема версионности

     а) Контентные хэши в именах ВСЕХ build-артефактов.
        В angular.json production уже стоит outputHashing: "all"
        (строка 52) — ОСТАВИТЬ и не понижать. Тогда main-ABC1234.js меняется
        в имени при любом изменении кода, и max-age=600 перестаёт быть
        проблемой: старый файл физически не может «закэшироваться вместо
        нового», у него другой URL.
        Исключение-правило: sw.js НЕ хэшируется (у SW должен быть стабильный
        URL, иначе он не сможет обновлять сам себя).

     б) manifest сборки (sw-manifest.json), генерируется на build из
        ФАКТИЧЕСКОГО списка файлов dist/.
        Критично: в прекеш попадают только реально существующие файлы.
        Добавление несуществующего пути валит cache.addAll, и SW молча не
        активируется (это уже ломало PWA avtoklavi: 146 картинок в прекеше).
        Обязательная проверка на build: каждая строка manifest существует на
        диске, иначе сборка падает.

     в) Идентификатор сборки.
        Файл src/environments/version.ts генерируется prebuild-скриптом:
          { app: "0.1.0", sha: "<git rev-parse --short HEAD>",
            builtAt: "<ISO>", buildId: "<sha>-<unix-ts>" }
        Тот же buildId пишется в sw-manifest.json и в начало sw.js константой.
        Версия приложения = buildId, виден в настройках (11.4).

     г) Схема данных версионируется НЕЗАВИСИМО от версии приложения.
        DB version (8.2) и schema у записи (8.3) — отдельные счётчики.
        Реестр миграций: массив { from, to, migrate(tx) }. Любое повышение
        DB version обязано иметь запись в реестре, иначе старт падает в
        понятную ошибку, а не в тихую порчу данных.

11.5.3. Как именно «сразу подтягивается» (алгоритм, обязателен к реализации)

     1. index.html и sw-manifest.json обслуживаются СТРОГО network-first,
        без кэша (это единственные два файла, где кэш запрещён — всё остальное
        можно держать в кэше вечно, потому что оно хэшировано).
     2. При старте приложения: registration.update().
     3. Дополнительно update() вызывается:
          - на visibilitychange → visible (возврат в приложение);
          - на focus окна;
          - каждые 30 минут по таймеру (если приложение открыто);
        Это обходит правило «браузер сам проверяет SW редко»: явные вызовы
        не подпадают под 24-часовой троттлинг так же сильно, как фоновые.
     4. При updatefound → installed, если уже был контроллер — НЕ
        перехватывать страницу молча: показать баннер «Доступно обновление»
        (11.4). Причина: тихий reload может выбросить из незаполненной формы.
     5. После нажатия «Обновить» — postMessage SKIP_WAITING →
        controllerchange → location.reload(), с сохранением текущего
        роута и несохранённого ввода (в sessionStorage/через store).
     6. Картинки TMDb (image.tmdb.org) — stale-while-revalidate, они
        неизменяемы по URL, поэтому их можно кэшировать агрессивно (11.2).

11.5.4. Что запрещена эта схема гарантирует (и это надо сказать честно)

     - Изменение ЛЮБОГО файла кода/стилей/картинки в main → новый buildId →
       новый sw-manifest → SW видит другой байт-код sw.js (в нём вшит
       buildId) → предлагает обновление. То есть «подтягивается сразу»
       выполняется в пределах одного запуска/возврата в приложение, а не
       мгновенно для закрытой вкладки.
     - Для полностью закрытого PWA первое открытие может отдать старый
       index.html (до 10 минут из-за max-age=600). Обойти это на Pages
       нельзя никак. В UI это лечится тем, что обновление предлагается
       всегда при старте (п.2), а не «когда-нибудь фоном».

11.5.5. Релизная дисциплина

     - Семвер в package.json; на каждый релиз — git tag vX.Y.Z и запись в
       CHANGELOG.md (ведение — вручную или по conventional-commits,
       release-please из донора удалён, 2.5).
     - Деплоится ТОЛЬКО тег или main (17.2); артефакт сборки хранится как
       release-ассет, чтобы можно было откатить, не пересобирая.
     - Запрещено выкатывать сборку, где sw-manifest.json не совпадает по
       buildId с тем, что вшит в sw.js: это состояние «никогда не
         обновится», ловится тестом в CI (16).

12. ОСОБЕННОСТИ ПЛАТФОРМ (iOS — приоритет)

12.1. Риск потери данных (главный риск продукта)

     Факт: браузеры чистят хранилище сайта при нехватке места и при
     длительном неиспользовании. На iOS для НЕ установленного Safari-вкладочного
     контента данные могут быть вычищены через 7 дней (ITP); для
     установленного на домашний экран PWA это правило мягче, но НЕ отключено.
     Обязательные меры:
       - при первом запуске показать баннер «Добавьте на домашний экран»
         (для iOS — с картинкой-инструкцией, т.к. жест не автоматизируется);
       - вызвать navigator.storage.persist() и ПОКАЗАТЬ результат
         (строка в настройках «Хранилище закреплено: да/нет»);
       - показывать занятость хранилища (usage/quota из estimate()) — в
         доноре оценка квоты есть, но на 10 МБ localStorage (8.1), переписать
         на реальные цифры IndexedDB;
       - раз в 14 дней, если пользователь ни разу не выгружал бэкап, —
         мягкое напоминание «Сделайте резервную копию».
     Никаких обещаний «данные не потеряются» в UI.

12.2. Viewport и safe-area

     - viewport-fit=cover (в доноре есть) — сохранить.
     - НЕТ maximum-scale=1.0,user-scalable=no: в доноре они стоят, и это
       нарушение WCAG 1.4.4 (невозможно увеличить текст). Удалить, заменив на
       корректную вёрстку (жесты pinch у image-viewer не сломаются — он
       считает свой zoom сам).
     - Все фиксированные слои: padding-top: env(safe-area-inset-top),
       tabbar: padding-bottom: env(safe-area-inset-bottom).
     - Высота: 100dvh с фолбэком 100vh; для листов — --kd-lvh через
       visualViewport.height. На iOS 100vh = высота без учёта панели Safari,
       это классическая причина «уезжает кнопка».
     - При открытии клавиатуры: слушать visualViewport, скроллить активное
       поле в центр; НЕ полагаться на Ionic Keyboard (он был Capacitor-модуль,
       удалён в 2.4).

12.3. iOS-специфика, которую нельзя игнорировать

     - Push-уведомления: недоступны в PWA на iOS (Web Push с iOS 16.4 только
       для установленных, и требует HTTPS + св — но фичи пушей в продукте нет,
       поэтому просто НЕ обещать их нигде).
     - navigator.vibrate: не поддерживается → no-op (2.4).
     - «Поделиться» (Web Share API) — поддержать, если есть, иначе — скачать
       файл.
     - File System Access API — нет, загрузка бэкапа только через
       <input type="file"> (в доноре так и есть, строки 387–423 settings).
     - Долгий press на постере конфликтует с системным вырезанием текста на
       iOS: обязательно -webkit-touch-callout: none и user-select: none на
       интерактивных постерах.
     - Двойной тап по картинке в image-viewer: отключить системный zoom
       (touch-action).
     - iOS обрезает длинные подписи под иконкой ~11–13 символами — отсюда
       short_name в 11 символов.

12.4. sessionStorage ≠ хранилище

     Донор кладёт pre-import snapshot в sessionStorage (1903–1912). В PWA
     sessionStorage живёт до закрытия вкладки, а iOS убивает вкладку
     «в фоне» — откат импорта становится невозможен ровно тогда, когда он
     нужен. Перенести в IndexedDB store 'snapshots' с TTL 30 дней.

12.5. Android/desktop

     - Desktop ≥1024px: контент в max-w контейнерах (6.4 донорского аудита),
       аналитика 1→2→3 колонки, sticky навигация по годам.
     - Мышь: hover-состояния обязательны (на touch их не существует —
       использовать @media (hover: hover)).
     - Клавиатура: «/» — фокус в поиск, «n» — быстрая запись, Esc — закрыть
       оверлей. Обязательный focus-trap в модалках.

13.3. ПОЛИТИКА ЧЕСТНОСТИ (обязательна, это ответ на системную проблему донора)

     приписывали аудиту, в коде ОТСУТСТВУЕТ — не «чинить».)

     Правила для Кинодневника:
       1. Любая цифра либо точная, либо с префиксом «~» и чипом покрытия
          («по 412 из 1066 записям»).
       2. Если данных меньше порога — «нет данных», а не среднее. Пороги

          помечено слабым местом.

          плитку статистики — не рисовать красивую пустоту.
       5. Никаких «прогнозных» рангов без чипа «предварительно».
       6. Скелетон до готовности мемоизированной статистики (мемоизация по
          (год, число записей, число обогащённых) — как в их аудите).

15. КЛЮЧ TMDb (требование пользователя)

15.1. Что сделать

     Ключи предоставлены заказчиком (v3 + v4 read token), проверены рабочими.
     Значения в этот документ и в репозиторий НЕ заносятся — они вводятся
     пользователем на устройстве.

     - В репозитории ключа НЕТ. Ни в environment.ts, ни в environment.prod.ts,
       ни в дефолтах настроек. В доноре ключ захардкожен (environment.ts:6,8)
       — при переносе обнулить.
     - Хранение: IndexedDB store 'settings', ключ 'tmdbApiKey'. Только на
       устройстве.
     - UI: раздел «Настройки → Данные TMDb → Ключ API»:
         • поле ввода (mask, показ/скрытие), кнопка «Проверить»;
         • проверка реальным запросом к /configuration, ответ «Ключ рабочий»
           / «TMDb ответил 401»;
         • подпись: «Ключ нужен, чтобы приложение находило фильмы. Он хранится
           только на этом устройстве и уходит только на api.themoviedb.org.»
     - Если ключа нет — приложение работает: дневник, списки, аналитика,
       сохранённые тайтлы доступны; поиск и добавление новых тайтлов дают
       понятное сообщение с кнопкой «Ввести ключ». НЕ падать, НЕ показывать
       пустые экраны.

15.2. Публичность ключа — честная формулировка

     Клиентское PWA без бэкенда физически не может спрятать ключ: он виден в
     инструментах разработки у любого, кто откроет сайт. Это нормально для
     TMDb (v3-ключ публичен по своей природе), но в UI и README это надо
     сказать прямо, а не создавать ложное впечатление секретности.
     Поэтому в описании поля — «хранится только на устройстве» (правда: мы
     его никуда не отправляем), но НЕ «секретно».

15.3. Запрещено

     - класть ключ в бандл, в git, в экспорт бэкапа, в localStorage-логи,
       в консоль, в URL (в доноре ключ улетает в query — это принято TMDb,
       но в логах/закладках его быть не должно: не показывать URL запроса
       в UI и не сохранять в истории).
     - предлагать «общий демо-ключ» в README.
